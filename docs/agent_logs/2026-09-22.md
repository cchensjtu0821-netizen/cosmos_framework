## `RESOLVED` Custom real-robot teleoperation SFT feasibility

- Finding: custom teleoperation data can train the action-policy path. Each
  adapted sample must provide video, a time-aligned action chunk, task text,
  conditioning FPS, policy mode, viewpoint, and an embodiment domain ID.
- The model interface supports raw action widths up to the configured 64
  channels: preprocessing pads real actions and records `raw_action_dim`, and
  training masks padded channels.
- Direct reuse of the DROID adapter is appropriate only for its exact robot and
  schema assumptions (Franka seven joints plus gripper for the 8-D joint action,
  DROID LeRobot feature names, and its three-camera composition). A different
  robot/action convention needs a dataset adapter plus a distinct domain-ID
  registration; data should preferably be converted to LeRobot v3 first.
- Recommended sequence: validate one decoded sample and one batch, run a
  1--10-step Edge GPU smoke job, then tune learning rate, trainable modules,
  action normalization, chunk length, and batch/accumulation for the full run.

### Dataset metadata received

  episodes, 1,366,169 frames, two tasks, and three 320x240 H.264 streams
  (`cam_high`, `cam_left_wrist`, `cam_right_wrist`). This is about 12.65 hours,
  with an average episode duration of about 39.7 seconds.
- Available control/state channels support a symmetric 27-D joint-space
  contract if all components are required: per arm 7 joints + psi + gripper,
  plus 6 torso joints and 3 base-speed channels. A 25-D Cartesian alternative
  also exists, but the deployment controller semantics must determine which
  representation is authoritative; do not mix both in one target vector.
- The large episode-table printout is per-episode metadata plus nested field
  statistics, not raw training rows. It shows task text and per-camera video
  timestamp/file mappings but should be re-queried with `stats/*` columns
  excluded.
- The dataset size is plausible for narrow two-task SFT. Train/validation must
  split by episode, and action-command/state timestamp alignment plus the exact
  command-to-actuation convention remain validation requirements.

### Normalization metadata

- `meta/stats.json` has entries for all MOZ1 command/state/video/index fields,
  consistent with a complete LeRobot v3.0 export.
- `norm_stats.json` currently exposes only a top-level `norm_stats` wrapper.
  Cosmos' generic action-stat loader expects `mean`/`std`, `min`/`max`, or
  `q01`/`q99` arrays either at the top level or under a requested block, so the
  nested structure must be expanded and converted into the exact assembled
  action-vector order before it is usable.
- The supplied per-episode excerpts show `base_cmd_speed` very close to a
  constant/zero value. Confirm from global statistics; if stationary across
  the corpus, exclude base speed from the first policy target rather than
  spending three action channels and loss weight on it.
- The nested wrapper is now confirmed as two objects, `state` and `actions`,
  each containing `mean`, `std`, `q01`, and `q99`. The action quantiles are the
  preferred robust-normalization source, but their array length and original
  dimension ordering must be established before adapting them. The generic
  Cosmos loader cannot consume the outer `norm_stats.actions` wrapper without
  either conversion to the expected action-only JSON schema or a MOZ1-specific
  loader override.
- All four `state` arrays and all four `actions` arrays have length 20. This
  proves the dataset producer used a pre-defined paired 20-D control contract;
  the earlier candidate 24/27-D layouts derived from the raw columns must not
  be combined with these statistics. Recover the 20-D field order from the
  producer or match its global mean/std blocks against `meta/stats.json`; if a
  different contract is chosen, recompute statistics for that exact vector.
- Mean/std block matching exactly recovered the 20-D state layout:
  `[leftarm_state_cart_pos(6), left_gripper_state(1),
  rightarm_state_cart_pos(6), right_gripper_state(1),
  torso_state_cart_pos(6)]`. Joint, psi, and base fields are not part of this
  established state contract.
- No raw command block matched the 20-D action mean/std exactly. The likely
  semantic pairing is the analogous Cartesian command layout, but an action
  time shift, relative-action transform, episode-boundary trimming, or data
  filtering must be ruled in/out before building labels. Compare the assumed
  block statistics numerically and inspect the dataset-generation code; do not
  silently use raw same-frame commands.
- Follow-up statistics establish that action dimensions 6 and 13 are absolute
  gripper commands (their mean/std match the raw command fields closely), while
  the three 6-D pose blocks are zero-centered relative pose targets. Their
  layout is therefore `[left relative Cartesian(6), left gripper,
  right relative Cartesian(6), right gripper, torso relative Cartesian(6)]`.
  The translation/rotation magnitudes are much larger than typical adjacent
  30-Hz deltas, suggesting an anchored or current-state-to-future-target
  transform rather than simple framewise differences, but the exact SE(3)
  formula and Euler convention still require provenance/code or candidate
  reconstruction validation.
- Clarification: zero-centered action mean/quantiles alone do not mathematically
  prove a relative-pose transform. The inference is supported jointly by the
  exact absolute-state field match, the large mismatch against raw absolute
  Cartesian commands, symmetric zero-centered pose-action ranges, and exact
  gripper-command alignment. Centering or another preprocessing transform could
  produce similar statistics, so only the generation code or candidate
  reconstruction against samples can establish the precise relative formula.
- The missing producer-side relative-action conversion is a material blocker to
  reproducing the 20-D labels exactly, but absolute state plus relative future
  actions is itself a supported Cosmos contract. The repository's standard
  Cartesian conversion is an SE(3) body-frame delta,
  `delta_T = inv(T_i) @ T_(i+1)`, followed by rotation re-encoding; it is not
  elementwise subtraction of XYZ/Euler vectors. The observed MOZ1 action scale
  still argues against assuming adjacent 30-FPS deltas. Next action is to test
  candidate framewise/anchored and timestamp-offset formulas against raw rows
  and the supplied 20-D action statistics (or recover producer/controller code)
  before implementing the dataset adapter.

## `RESOLVED` Provisional MOZ1 Edge training smoke path

- Implemented a MOZ1 LeRobot-v3 adapter that deliberately treats the three
  stored 6-D Cartesian action fields as already-relative values. It does no
  subtraction or SE(3) conversion. The model input is one absolute 20-D state
  row followed by 16 direct 20-D action rows, padded by the shared transform to
  64 channels.
- State and action rows use their respective `norm_stats.state` and
  `norm_stats.actions` quantile blocks. The adapter validates 20-D finite stats,
  feature widths, camera-window lengths, native 30 FPS, and finite samples.
  Semantic idle-frame detection is disabled until the relative rotation and
  reference-frame convention are known.
- Registered embodiment `moz1` as domain 21 with raw width 20, added the
  `action_policy_moz1_edge` 10-step smoke experiment, and added a CPU-side
  sample inspection entry point. The experiment uses 17 video/state-action
