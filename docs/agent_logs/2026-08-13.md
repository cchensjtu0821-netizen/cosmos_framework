## ONNX external-data `.pb` naming

Status: `RESOLVED`

- ONNX external tensor data does not require a `.data` suffix. A single
  `model.onnx.pb` external file is valid when the main ONNX tensor metadata
  records that relative filename in each external-data `location` field.
- Renaming only the existing `.onnx.data` file is insufficient because the
  main model would retain stale `.data` references. The current exporter and
  simplification repack path explicitly choose `<model>.onnx.data`, while the
  shell pipeline defaults OMG `--weight` to that same path.
- Supporting `.onnx.pb` cleanly requires parameterizing the converter's
  external-data filename and passing the resolved path to OMG. The `.pb` file
  remains raw external tensor bytes; the suffix does not turn it into another
  ONNX ModelProto.

Validation evidence: inspected `convert_cosmos3_to_onnx.py` external-data
consolidation and `run_cosmos3_quant_onnx_full.sh` Step 4/9 path handling. No
model was repacked and no ONNX checker, ORT, OMG, or OMC validation was run.

## ONNX opset 12 compatibility question

Status: `RESOLVED`

- External-data serialization and ONNX opset are independent. Choosing a
  `.pb` `location` in `onnx.save_model` does not convert or constrain the
  model's `opset_import`.
- The current Policy exporter intentionally targets opset 18. It cannot be
  safely changed to 12 as a filename/metadata-only adjustment because Step 5
  creates `ScatterND(reduction=add)` as an exact intermediate lowering, while
  the `reduction` attribute is only defined for ScatterND starting at opset 16.
  Step 5 runs `onnx.checker` before Step 6 lowers that intermediate, so an
  opset-12 declaration would be structurally invalid in the current sequence.
- If a deployment tool strictly requires opset 12, it needs a separate
  compatibility project: export/down-convert a candidate, rewrite every
  post-opset-12 schema use before declaring opset 12, then run checker,
  structural audit, original-versus-candidate output comparison, and OMG/OMC.
  Merely editing `opset_import` is not a valid conversion.
- Opset 12 was introduced with ONNX 1.7.0/IR 7, but the Python package does
  not have to be exactly 1.7. A newer ONNX package can load and check an
  opset-12 graph. Backend acceptance must be checked independently for both
  `ModelProto.ir_version` and every domain in `opset_import`; an older compiler
  may accept opset 12 yet reject a newer IR version emitted by a modern
  exporter. ONNX Runtime 1.16.3 is broadly new enough for opset 12, but that
  does not establish private OMG/OMC support.

No code was changed for opset selection. Local ONNX validation remains
unavailable because this workspace has no `onnx` package.

## Cast nodes after ONNX simplification and finalization

Status: `INVESTIGATING`

- Both Policy export paths simplify with `onnxslim`. The quantized full
  pipeline performs in-place simplification during Step 4 and records
  `onnx_simplified=true`; it deliberately uses `no_shape_infer=true` for the
  multi-GB external-data model.
- Simplification occurs before the compatibility/finalization passes. Step 5
  subsequently inserts an INT64 Cast before every GatherND/ScatterND without
  first checking whether the indices are already INT64. Step 6 lowers many or
  all of those ND consumers to Slice/Add/Concat forms, but it has no general
  reachability prune or second simplification pass afterward.
- Consequently, the final ONNX can contain two distinct Cast classes: required
  dtype boundaries retained from export (floating compute, masks, shape/index
  tensors), and genuinely dead/no-op Casts introduced or exposed after Step
  4. Historical finalized graphs contained 190 Cast nodes; node count alone
  cannot determine which class a particular current graph belongs to.
- Do not run an unconstrained final `onnxslim` as a deployment fix: it may
  change the Gemm/MatMul nodes and names used by the quant-parameter matching
  contract. First classify Cast consumers and source/target dtypes. Removing
  only graph-unreachable nodes is semantics-preserving and name-stable, but
  still requires checker, strict audit, quant-name coverage, and server-side
  output comparison.

Next action: inspect the exact raw, compatible, and final ONNX Cast counts,
