## ONNX Runtime CUDA equivalence verification failure

Status: `RESOLVED`

- The full quantization script reached compatibility rewrite Step 5; the
  original graph failed while executing `node_einsum` during numerical
  equivalence verification, before rewrite equivalence could be established.
- ONNX Runtime selected `CUDAExecutionProvider`, but its CUDA Einsum kernel
  could not load `libcudnn.so`. Listing both CUDA and CPU providers does not
  retry a node on CPU after a CUDA kernel fails at runtime.
- Immediate diagnostic workaround: run verification with only
  `CPUExecutionProvider`. Preferred GPU resolution: make the cuDNN version
  required by the installed `onnxruntime-gpu` visible to the dynamic loader,
  then rerun the complete rewrite and require finite/allclose output.
- Repository setup normally clears `LD_LIBRARY_PATH`, while each pipeline step
  runs in a separate Python process. Step 4 may therefore use PyTorch-bundled
  cuDNN successfully without making that library discoverable to the fresh
  ONNX Runtime process in Step 5. The verifier currently imports ONNX Runtime
  without first importing PyTorch or calling `onnxruntime.preload_dlls()`.
- ONNX Runtime's documented PyTorch-compatibility path is to import PyTorch
  before creating CUDA sessions, or (ORT 1.21+) call `preload_dlls`; this is the
  leading explanation to confirm with a minimal server probe before changing
  packages or library symlinks.
- Server probe confirmed a compatible stack: PyTorch 2.12.1+cu130, ORT 1.28.0
  built for CUDA 13.0, and cuDNN 9.20. `preload_dlls(directory="")` found and
  loaded the versioned cuDNN libraries from the environment's NVIDIA
  site-package directory. The process `LD_LIBRARY_PATH` contained CUDA toolkit
  directories but not that cuDNN directory, confirming library discovery—not
  installation or major-version compatibility—as the failure cause.
- Resolution: preload the NVIDIA site-package libraries in the rewrite
  verifier before constructing either CUDA session.
- Implemented CUDA verification preloading with
  `onnxruntime.preload_dlls(directory="")`; older ORT versions fall back to
  importing PyTorch before session creation. The verification report records
  which preload method was used.
- Added a Step 5 resume mode to the full quantization script. It preserves the
  existing quantization directory, requires the raw fake-quant ONNX, skips
  Steps 1–4, and starts at compatibility rewriting/equivalence verification.
- Server Step 5-only validation completed successfully after the preload fix.
  Both `vision_velocity` and `action_velocity` were finite with nonfinite
  counts `(0,0)`, `allclose=True`, and zero maximum/mean absolute error. The
  compatible ONNX, prompt embedding sidecar, and rewrite report were saved;
  Steps 6 onward were intentionally not run by this validation command.
- After that isolated validation succeeded, the switch was generalized to
  `COSMOS3_START_STEP5=1`: it now continues through Steps 6–10. The old
  `COSMOS3_ONLY_STEP5=1` name remains accepted as a compatibility alias with
  the new resume-through-completion behavior.
- A shell smoke test with mocked Python calls confirmed the resume mode invoked
  Steps 5, 6, 7, and 8 in order, reached cleanup, and never invoked Steps 1–4;
  OMG was disabled in that local control-flow test. Real finalization, audit,
